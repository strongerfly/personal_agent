# 阅读、知识库与个人成长：调研决策记录

第 1–7 节核验日期：2026-09-28；第 8 节 Edict 源码对照新增于 2026-09-29。范围为公开官方资料、项目原作者文档与研究论文；未登录微信读书或 Obsidian，未读取用户凭证，未验证用户账号连通性。

账号和知识库继续保留配置入口。下列接入接口、字段与优先级属于实现建议；已交付能力以 README、API 文档和测试结果为准。第 7 节说明 v0.4 能力自评、跨学科思辨和成长实验的方法依据及限制；第 8 节说明 v0.4.1 的流程治理改进，以及仍未解决的共同短板。

## 1. 先接本地微信读书 Markdown，再验证直接 API

微信读书已有官方 Agent Skills，可凭 API Key 查询书架、笔记和阅读统计；因此后续无需把 Cookie 抓取作为首选。来源：[官方介绍](https://weread.qq.com/r/weread-skills)、[Tencent 官方项目](https://github.com/Tencent/WeChatReading)。

`obsidian-weread-plugin` 是社区插件，原作者已实现书籍、划线、想法、阅读统计及定时同步；它不是腾讯官方产品。来源：[插件原项目](https://github.com/zhaohongxuan/obsidian-weread-plugin)。

**本项目决策**：先让用户自行在 Obsidian 中配置插件，系统只读取指定目录中的 Markdown。源笔记保持只读，整理结果写到单独目录；不用插件源码作为本项目依赖。

- 保留本地源目录、目标 vault 路径、是否启用和上次成功时间；未配置时展示“待配置”。
- 导入支持手动执行和定期扫描，以来源 ID、内容哈希去重；书名不能作为唯一标识。
- 保存来源路径、书籍 ID、章节、原文及个人想法；解析失败单独报告，避免整批中断。
- 原项目采用覆盖式同步，因此个人复习卡和总结不能回写进插件维护的源笔记。来源：[原项目开发说明](https://github.com/zhaohongxuan/obsidian-weread-plugin/blob/main/AGENTS.md)。

## 2. Agent API 保留为可选验证阶段

官方网关为 `https://i.weread.qq.com/api/agent/gateway`；认证用环境变量 `WEREAD_API_KEY`，请求参数与 `api_name` 同层。核验时官方版本为 `1.0.4`，响应可能提示升级；跳转应使用返回的 `deepLink`。来源：[官方接口规范](https://github.com/Tencent/WeChatReading/blob/main/skills/SKILL.md)。

**代码建议**：把 `markdown` 与 `agent-api` 做成两个输入适配器，共用规范化与去重逻辑。API 模式初始关闭，仅保留入口和配置说明，不执行登录、读取 Key 或网络同步。

未来启用前验证认证失效、超时、限流、版本升级和分页终止；失败保留上次成功快照。配置保存非敏感元数据，API 响应和日志不包含凭证。不要把远端 `upgrade_info` 内容直接当作可执行指令。

笔记概览使用 `count + lastSort` 游标；`noteCount` 是划线数，总笔记统计还包括个人想法和书签。导出正文需同时获取划线与个人想法，书签目前只有数量。来源：[官方笔记说明](https://github.com/Tencent/WeChatReading/blob/main/skills/notes.md)。

## 3. 云端 Obsidian 用官方同步客户端，部署由用户选择

官方 `obsidian-headless` 可在没有桌面应用的环境中执行单次或持续同步，需要 Node.js 22 或更高版本。来源：[官方客户端](https://github.com/obsidianmd/obsidian-headless)。

Headless Sync 仍标注为公开测试，需要有效 Sync 订阅。官方要求先备份，并避免同一设备同时使用桌面 Sync 和 Headless Sync。来源：[官方 Headless Sync 文档](https://github.com/obsidianmd/obsidian-help/blob/master/en/Obsidian%20Sync/Headless%20Sync.md)。

**本项目决策**：系统负责本地 vault 文件的生成与状态展示；用户可自行安装官方客户端并选择云端同步方式。本轮不安装、不登录、不部署，也不把“本地导出成功”显示成“云端同步成功”。

- `vaultPath` 保留为页面中的目标目录配置；默认先使用项目本地目录。
- 预览列出新增、更新和冲突；确认后才写入。禁止越界路径，写入前检查文件是否被外部修改。
- 独立维护生成文件清单与内容哈希；不覆盖 vault 根目录 README，不删除用户文件。
- 未来可通过客户端 `sync-status --json` 读取同步状态；“未配置、待同步、已同步、失败”分开展示。

## 4. 统计要区分投入、回忆和实际产出

微信读书的 `totalReadTime` 单位为秒，统计基于自然周/月/年；它应作为完整周期总量，日级明细用于边界校验。来源：[官方阅读统计说明](https://github.com/Tencent/WeChatReading/blob/main/skills/readdata.md)。

**代码建议**：区分累计快照与每日增量，保存 `periodStart`、`periodEnd`、`sourceUpdatedAt` 和统计口径。同一快照重复导入不累加时长；同日的手工记录与平台数据按来源展示，未经核对不相加。

日报/周报分别显示阅读投入、新增知识、已完成复习和带证据的任务；缺失数据标记未知，不填成零。每个指标保存来源记录 ID，使用固定时区和半开区间 `[start, end)`。

“读了多少”和“掌握多少”分开统计。任务验收保存 `evidence`、`completedAt` 与关联知识项；学习输出可以是一段解释、一份练习结果或实际项目产物。这是本项目的产品设计选择，不能仅凭时长推算掌握度。

## 5. 把笔记变为主动回忆，再按结果安排复习

原始实验发现，回忆测试相较重复阅读对延迟记忆更有帮助；用户的熟悉感不能替代真实回忆结果。来源：[Roediger 与 Karpicke，2006](https://pubmed.ncbi.nlm.nih.gov/16507066/)。

间隔练习的研究说明，合适间隔与希望保留知识的时长有关；不能宣称一套固定天数适合所有内容。来源：[Cepeda 等，2006](https://pubmed.ncbi.nlm.nih.gov/16719566/)。

**代码建议**：先让用户确认可编辑的问答卡；答题前隐藏答案，提交后展示来源，再选择“忘记、困难、记得、轻松”。保留真实回答、评分、时间和下次到期日；未回答不能标记已掌握。

第一版可用公开标明为启发式的简单间隔，提供每日上限、暂停和撤销。后续若引入 FSRS，原作者的 `ts-fsrs` 支持评分后计算下次日期，需要 Node.js 20+，采用 MIT 许可。来源：[TS-FSRS 文档](https://open-spaced-repetition.github.io/ts-fsrs/)、[许可证](https://github.com/open-spaced-repetition/ts-fsrs/blob/main/LICENSE)。本轮不新增该依赖。

## 6. 下一步优先级与验收

- **P0 — 本地闭环**：导入 → 去重 → 知识整理 → 回忆/任务 → 完成证据 → 日周报 → Obsidian 预览与导出。重复执行不增量膨胀；每个结论可找到来源。
- **P0 — 稳定运转**：定时运行持久化状态，支持重启补跑、失败重试和单实例锁。模拟跨日、跨周、时区边界及写入中断；实际用户数据不进入测试。
- **P1 — 真实账号验证**：由用户配置账号后，用少量书籍验证官方 Agent API；核对分页、笔记口径与时长，成功后才开放自动同步。
- **P1 — 云端验证**：由用户选择并配置同步方式，先在测试 vault 验证双端修改和冲突，再验证报告同步；不把部署准备当成部署完成。
- **P2 — 自适应学习**：累计真实回忆记录后评估 FSRS、目标关联和输出质量；模型摘要只能给建议，保留原文与人工修正。

本轮调研未安装外部组件、未复制第三方源码、未访问用户凭证。社区插件与官方 API 分别记录来源，后续接口变化需重新核验。

## 7. v0.4：用证据、分歧和实验支持个人成长

这一版本的设计问题是：如何把“多角度思考”转成可持续的行动和复盘，而不把模型生成的长篇分析包装成事实或能力测量。产品采用场景自评、竞争解释、因果假说、小实验和策略记忆；以下资料为方法启发，不能据此声称系统已实现经过实证验证的科学量表、自动因果识别算法或个人成长预测。

### 7.1 把关联、干预和反事实区分开

Pearl 对因果推理的讨论区分了从观察中发现关联、研究干预影响与回答反事实问题；不同问题需要不同假设，不能仅凭共同出现或时间先后自动跨越到因果结论。来源：[Pearl：The Seven Tools of Causal Inference](https://ftp.cs.ucla.edu/pub/stat_ser/r481.pdf)。

**产品决策**：思辨结果中的因果链必须同时写出候选原因、结果、机制、替代解释和检验。离线模式给出填空及对照提示；AI 模式生成待验证假说，不宣称已经控制混杂、完成随机实验或识别真实效应。历史类比也必须检查背景与适用条件，不能把“以前如此”直接转成“这次必然如此”。

### 7.2 机会成本让取舍可以被讨论

经济学关于稀缺与选择的基本问题提醒我们：选定一种投入，意味着放弃其他可行用途，收益需要结合被放弃的机会理解。来源：[OpenStax：Choice in a World of Scarcity](https://openstax.org/books/principles-economics-3e/pages/2-introduction-to-choice-in-a-world-of-scarcity)。

**产品决策**：战略取舍维度与经济视角要求比较真实可选方案、时间成本和退出条件。实验保留预计投入、基线和目标，不能只展示成功结果而忽略成本。当前没有读取财务账户，也不自动作投资或预算决策。

### 7.3 东西方哲学用于提问，不冒充原话

儒家讨论学习、思考、修养与关系责任，可启发对具体承诺和行为的一致性检查。来源：[Stanford Encyclopedia of Philosophy：Confucius](https://plato.stanford.edu/entries/confucius/)。

有关老子的讨论提示，“无为”不能简单等同于完全不行动，它涉及行动方式、控制与人为干预等问题。来源：[Stanford Encyclopedia of Philosophy：Laozi](https://plato.stanford.edu/entries/laozi/)。

实用主义强调通过经验及实际后果澄清观念和探究问题；“有用”仍须说明对谁、在哪种条件下、以什么代价成立。来源：[Stanford Encyclopedia of Philosophy：Pragmatism](https://plato.stanford.edu/entries/pragmatism/)。

**产品决策**：儒家视角追问责任与边界，道家视角追问过度控制与必要行动，实用主义视角追问可观察后果。正反双方都应提出最强理由，而非把东方或西方传统描写成单一立场，也不必强求所有分歧达成一致。系统不扮演圣贤，不捏造引语；一个模型写出的多个视角也不等于多个独立专家相互验证。

### 7.4 反证是修正解释的入口

可证伪性要求理论对可能观察作出有风险的承诺；但实际检验还涉及测量与辅助假设，单个不符预期的观察并不自动告诉我们究竟哪一环错误。来源：[Stanford Encyclopedia of Philosophy：Karl Popper，2017 存档](https://plato.stanford.edu/archives/spr2017/entries/popper/)。

**产品决策**：每个视角必须附带反方追问和区分解释的检验，实验提前记录指标、基线、目标与复查时间。复盘允许“支持、否定、证据不足”，不迫使用户把复杂结果归为成功/失败两类。反对意见针对论证与行为；直面问题不需要依靠羞辱、人格标签或凭有限数据诊断个人。

### 7.5 用行动后复盘连接下一轮调整

美国陆军公开材料中的行动后复盘方法围绕预期、实际、差异原因与后续改进展开，强调从具体执行中学习。来源：[People First Task Force Handbook](https://api.army.mil/e2/c/downloads/2023/01/31/692c03bc/22-06-672-people-first-task-force-handbook.pdf)。

**产品决策**：成长实验开始后生成真实任务，完成并记录证据后才能复盘。用户写下实际观察、所得与后续调整，再选择保留、调整或停止策略。否定或证据不足时不能直接保留；归档记录和完成证据不可覆盖，下一轮另建实验。军事方法在这里用于目标、资源、预案和学习，不把普通合作关系默认当作敌我对抗。

### 7.6 六边形与策略记忆的解释边界

六维和 1–5 级行为锚点是本项目的产品分类，尚未进行心理测量学验证。自评依据可以引用任务、笔记、签到和目标；完成数量不自动转成能力分，未评价维度保持未知。4–5 分优势与1–2 分练习方向只描述最近一次自评，不是人群比较、稳定人格结论或健康诊断。

无 AI 配置时，系统可以保存自评、生成诚实的思辨工作单、追加本人对正反论点和因果检验的推演、建立并执行实验、复盘策略。配置模型后，案例、选中记录、方法定义及最近策略记忆均先预览再发送；模型需要引用已提供的记录，不能假装访问外部网页。理论链接只解释方法来源，不证明用户案例中的事实。

“系统自我成长”的当前实现是积累可追溯策略，并在后续分析中重新审查其适用性。它不会改变模型权重、自治修改程序、替用户批准外部动作，或因一次实验结果就自动提高任务强度。日周报与 Obsidian 导出负责让成长记录持续进入已有知识流程；云端同步和真实模型效果仍需用户配置后验证。

后续评价优先观察：建议是否帮助发现遗漏、是否减少反复犯同一错误、实验是否产生可解释的结果，以及付出的时间是否值得。对比应保留失败和证据不足的案例，不能仅用自评分上涨、分析篇数或连续使用天数证明系统有效。

## 8. v0.4.1：开源 Edict 三省六部对照与融合

### 8.1 核验对象与方法

本次按最符合“三省六部”描述的 [cft0808/edict](https://github.com/cft0808/edict) 开展核验，固定提交为 [`14a207557719c046af0f993a7bff1cc5a5015b33`](https://github.com/cft0808/edict/tree/14a207557719c046af0f993a7bff1cc5a5015b33)。结论来自公开源码静态检查，不是安装后的端到端验证；没有运行其安装器、连接模型或将其加入本项目依赖。本项目只借鉴设计思路，没有复制第三方源码。仓库定位如有变化，应以具体提交而非项目名称对照。

它把消息分流、规划、审议、派发与部门执行组织成有看板和历史的流程。值得学习的是让工作状态、退回与人工干预可见，而不能仅凭官职数量、演示画面或 README 的对比宣传推断实际完成质量。

### 8.2 如何实现，以及哪些优点成立

- **流程显式化**：`kanban_update.py` 定义状态转换与角色范围，执行状态变化前校验；Dashboard 配套停滞检测、重试、升级与阻塞处理。由这些实现可以确认其关注任务治理，而非只有聊天界面；它们是否覆盖所有运行分支仍需分别核查。[状态机与命令实现](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/scripts/kanban_update.py)、[Dashboard 调度扫描](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/dashboard/server.py#L1172)
- **审议维度具体**：门下角色要求检查可行性、完整性、风险与资源，并给出具体意见。这四项可以转成可保存的审议记录；其本身仍是提示词约束，不能等同于已验证的审查能力。[门下 SOUL](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/agents/menxia/SOUL.md#L4-L19)
- **人工干预有入口**：Dashboard 提供停止、取消、恢复操作；让不再值得推进的任务退出执行是合理能力，但仍须校验终态、保留证据并统一统计口径。[控制操作](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/dashboard/server.py#L182-L223)

运行方式必须区分：根目录 `start.sh` 启动 `scripts/run_loop.sh` 和 `dashboard/server.py`，后者属于轻量看板路径；`edict/backend/app/main.py` 是另一套 FastAPI/EventBus 入口。README 同时列出 stdlib、Redis Streams、Outbox 和 DAG，不能把这些条目都当成根目录一键启动已经启用的能力。本项目目前保留 Node.js 单进程与 JSON，不因对方存在新后端就引入数据库和消息队列。[启动脚本](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/start.sh#L63-L78)、[FastAPI 入口](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/edict/backend/app/main.py#L18-L54)、[README 技术亮点](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/README.md#L601-L615)

### 8.3 已验证短板与本项目对照

1. **审议次数不能替代质量。** 门下提示词存在“最多 3 轮，第 3 轮强制准奏”。限制循环有价值，强制放行却会让未解决问题进入执行；这是提示词规则的发现，不能断言每次运行都会发生。本项目旧流程虽无强制准奏，却允许批准意见为空，验收也只核对完成状态与证据非空，存在“流程通过但理由薄弱”的共同风险。v0.4.1 用四项审议理由与逐任务验收理由补齐记录，不引入自动放行。[门下原则](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/agents/menxia/SOUL.md#L86-L90)

2. **角色或状态规则需要覆盖所有入口。** Edict 的角色检查对未知身份存在放行分支，`cmd_state` 的校验不能证明其他直接写状态命令也执行同一规则；Dashboard 的停止、取消、恢复入口也需单独检查终态。该结论针对这些函数，不能据此泛化成整个平台均可越权。本项目同样没有独立登录身份，三省属于本人操作阶段；v0.4.1 增加受状态和版本约束的暂停、恢复与取消，完成与取消均禁止恢复，关联任务不能绕过暂停/取消继续修改。[角色检查与命令入口](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/scripts/kanban_update.py#L160-L166)、[Dashboard 控制入口](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/dashboard/server.py#L182-L223)

3. **朝议不等于独立模型交叉验证。** 朝议把全部官员资料放进一次模型请求来生成多方发言；失败会退回规则话术，结果未单独标明生成模式。本项目 AI 也由单模型提供多个视角，因此同样可能共享偏差；现有 `guided/ai` 标签与失败报错继续保留，不能将角色对话或格式合格当成真相。此处只描述朝议模块，不能反推 Edict 的所有执行 Agent 都是同一次调用。[朝议生成](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/dashboard/court_discuss.py#L498-L574)、[降级处理](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/dashboard/court_discuss.py#L147-L210)

4. **单次限制不等于完整运行治理。** 朝议具有请求超时与输出上限，但会话存于进程内；推进函数未核对结束态或累计轮次，调用函数仅返回文本，没有保存用量。本项目已有 30 秒超时、预览与版本检查，却仍可能对同一案例并发付费调用。v0.4.1 增加同案例互斥和通用分析互斥，直至保存结束再释放；持久账本、用量、累计预算和崩溃后供应商处理状态仍未解决。[朝议会话](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/dashboard/court_discuss.py#L112-L154)、[模型请求](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/dashboard/court_discuss.py#L430-L495)

### 8.4 本轮融合的实际边界

四维审议保存 `checks` 与 `gateVersion: 1`；逐项验收核对全部关联任务 ID、通过标记和理由，再冻结证据。旧版已批准但缺少现行审议标记的计划重新提交审议，保留历史；旧执行中计划使用新验收，旧结案保持冻结。这些校验强制说明判断依据，但仍不能自动鉴别套话、证据造假或错误因果。

暂停适用于已批准或执行中的计划，恢复回原状态；取消适用于全部未结案、未取消计划，取消后不可恢复。控制操作保存理由和版本；子任务及证据保留，未完成项退出今日、部门与概览活跃负荷和顺延建议，过去真实完成项仍计入历史产出。这是本地任务治理，不是中止外部工具或供应商运行中的请求。

AI 互斥只在本进程内有效。它与预览批准、过期检查、单次超时配合，减少并发重复操作；不能承诺进程崩溃后恰好执行一次，也不能把一次失败直接解释成未产生费用。本轮未增加第三方依赖、自治 Agent 或外部模型调用。

验证重点包括缺项/重复项/不通过项的审议与验收拒绝，旧批准计划重新送审，暂停与取消后的任务冻结和统计排除，历史完成数保留，结束态不可恢复，以及同案例并发请求与失败后释放。测试使用临时数据与本地模型替身，实际结果以 `npm test` 输出为准，不代表真实模型质量已验证。

### 8.5 仍需完成的优先级与验收

- **P0：AI 运行与消耗账本。** 持久保存运行 ID、输入快照摘要、状态、耗时、供应商 request ID 与返回的 token 用量；缺少用量标记未知。验证服务中断和重启后的“结果未知”，再增加累计预算和经用户决定的重试策略。当前内存互斥不满足此项。
- **P1：策略适用条件与反例。** 为策略保存适用场景、限制、反例、复查时间和后继实验；用相反情境案例验证不会无条件套用。当前只使用最近最多 8 条策略，尚无按适用范围的自动筛选。
- **P1：证据与语义质量。** 建立有可核对答案或人工复核的案例集，比较事实错误、遗漏、竞争解释、检验可行性以及时间成本；验证引用 ID 正确但内容不支持结论时能被识别或保留待核验。当前结构校验并未实现语义真伪判断。
- **P2：独立审议的收益。** 先比较单模型与独立审议在同一案例集上的增益与成本，再决定是否引入不同模型、上下文和角色权限。记录实际模型和资料来源，禁止只换角色名就宣传为独立专家共识。
- **P2：能力评价有效性。** 保留同类任务产出与外部反馈，说明测量场景与变化条件；未完成效度验证前仍称“能力自评”，不输出客观人群排名。六边形美观、分数上升和分析篇数都不能证明个人提升。

项目的优先顺序是让每次判断可追溯、每次行动可验证、每次错误能修正，再扩大代理数量与自动化范围。仍未验证的接入、真实数据效果与研究假说继续明确标注。
